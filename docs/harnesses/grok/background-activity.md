# Grok background activity

Grok's native TUI separates process Tasks (`Run`), Watchers (streaming `Monitor` processes and timed `Loop` registrations), and genuine Subagents. A Loop registration is a schedule; each native invocation can create a real child agent. Grok owns scheduling, overlap prevention, expiry, persistence and completion wakeups.

## Desktop presentation

Run and Monitor processes associated with a detached `commandExecution` Item use Desktop's **Background processes** section and terminal output. Genuine children use native child Threads. Neither gets a duplicate extension row. The Adapter reports the known `commandItemId` association, including retained completed associations in its bounded in-memory history; a restored process with no such association remains accessible as a process-typed supplemental row.

Loop schedules and unassociated processes appear in one extension-owned **Background activity** section inside the existing native thread-summary panel. Rows expand inline for native prompt/output, cadence, next-run timestamp and controls. There is no activity entry above the composer, portal fallback or separate full-height pane. The native Goal, Plan, slash menu, process UI and child navigation retain their own state and layout.

The section uses the native summary heading, row-label and secondary-text typography utilities, including dynamic-isle density variants. Its heading collapses the section without stopping discovery, polling or the schedule; reopening preserves selected row details. Temporary panel hiding retains this expansion state, and changing conversation resets it. Expanded Loop details show the first prompt line as a heading and place the remaining exact text under a collapsed **Schedule instructions** disclosure. Its open state survives polling; choosing another row resets it. Prompt text uses the panel font and process output retains monospace formatting. Instructions render as text, not executable markup.

The Grok activity list keeps every running or pending child, every Loop, and each Loop's `lastSubagentId` so `relatedActivityId` still resolves. Settled subagent rows are capped at the newest 20 in observation order. Host `thread/activity/list` materializes only running/pending children; a settled row may carry `threadId` from an indexed Mapping Store lookup and never from a full-store scan. Selecting a settled row calls `thread/activity/read`, which materializes that child. Re-linking an existing idle child after restart does not emit `thread/started`.

Loop invocations are tagged `origin: "scheduled"` from a live `scheduled.fired` identity or from a native `subagents/<id>/meta.json` prompt header that names a `scheduled_task_created` task. Host persists that origin on create and backfills existing child records once after the first successful activity list. Scoped `thread/list` (`parentThreadId` or `ancestorThreadId`) omits settled scheduled children so Desktop descendant discovery does not treat loop history as Subagents. A running scheduled child still appears. Direct `thread/read` and `thread/resume` of a scheduled child keep working, including Open latest run from the Background activity panel. Unscoped lists are unchanged.

Discovered child Threads expose the same native activity path convention as delegated children: their description/title, role or native child identity. Desktop can then place working children and completed-child counts in its normal compact Subagents summary. The full native Subagents tab retains completed history. This projection does not invent parent Turns or alter native child completion state.

Desktop's existing **Toggle summary** / **Toggle pinned summary** header action provides the native opening path for eligible local chats, independently of process or child rows. The extension does not open or pin the panel itself. That control's source placement is established for Desktop 26.1027.30824; Loop-only initial access remains an acceptance check. User screenshots establish mounting in a chat with concurrent native activity, rather than every possible opening state.

The versioned binding requires an active external conversation, its native workspace, exactly one visible summary root and one unambiguous native section container. Existing native sections identify their container. An initially empty panel can instead identify its content container through the native scroll/content wrapper relationship, without requiring a Context, process or child section. Hidden, ambiguous or unrecognized wrappers are rejected. The binding does not search localized headings or change native classes/styles. Missing, ambiguous or hidden panels leave no extension node; polling continues to discover actual activity and materialize running children. Settled rows without `threadId` open through activity read. A validated container may retain supplemental rows when its last native section disappears. A connected validated container is remembered across temporary hiding and revalidated before reuse; changing conversation clears that reference. Panel replacement, layout changes, context changes and disposal remove or retarget only extension-owned nodes. Default/dynamic-isle fixtures cover initial empty-container mounting and subsequent native-section appearance. Installed screenshots establish mounting for the shown mixed-activity state; installed empty-panel acceptance is recorded separately. This is a private DOM integration, not a supported Codex plugin UI slot.

Only running, scheduled or unknown supplemental activity keeps the section visible. A registry containing only native-represented processes, genuine children or terminal history leaves no extension node or spacing. While supplemental work continues, its completed results remain readable. Stable list/detail replies and unchanged clocks do not rewrite DOM.

- Process output/status comes from Grok's `x.ai/task/list`, scoped to the native parent Session, with native truncation preserved.
- Loop details use the native prompt, interval and next-run timestamp. Read-only `resources_state.json` supplies restoration because a scheduler-list ACP method is unavailable. Timestamps follow native `ScheduledTask.next_fire_at` and `pending_fire_at`; reaching the timestamp displays “Waiting for Harness.” Renderer countdowns never dispatch work.
- Live scheduler events and confirmed native deletions take precedence over persisted snapshots for the Session. Persistence refreshes restored schedules until their first live event; stale files cannot erase an observed schedule, replace its next-run state or restore a deleted one.
- **Stop task** calls native `x.ai/task/kill` with `clientUi`. **Delete schedule** calls native `x.ai/scheduler/delete`. Schedule deletion leaves genuine children with their own lifecycle; Desktop's native bulk terminal cleanup stops processes only.
- **Open latest run** resolves the actual related child through the current Host's activity list/read, then invokes the current parent conversation's native `onOpenBackgroundAgent` callback. The versioned binding requires an unambiguous committed React owner with matching parent conversation and Host IDs. Genuine external children are read-only, so Desktop opens its native Subagents panel and verifies descendant membership. Children need no main-sidebar row. Missing or conflicting ownership produces an explicit error; no URL, new-window or sidebar fallback is used. Generic child descriptors stay available independently of custom child presentation and a mounted section; list attaches an existing `threadId` without creating a record, and read materializes the selected child without a parent Turn.
- `/loop <interval and task>` uses the native slash-command handler. Grok interprets cadence and can ask for missing details. Host supplies no default interval.

## Public boundary

`HarnessSession.backgroundActivity` is an optional Session capability with `list`, `read`, `stop` and native child identities for Host materialization. Browser-safe schemas and `codexhost/thread/activity/{list,read,stop}` RPCs are shared across plugins. Host and Renderer contain no Grok-ID dispatch. Unsupported plugins return an explicit unsupported result; official Codex Threads keep their native behavior.

Activity reads and controls create no conversation Turns. Live scheduler children have session-level ownership and are never attached to an arbitrary subsequent parent Turn. Existing tool-spawn and goal-helper delegation Items keep their native owning prompt semantics. Background response history remains the existing autonomous-Turn mechanism with durable native identities and execution evidence. A Loop completion that persists while a user Turn is in flight does not fail or steal that user Turn; Host settlement keeps the matching `promptId`.

Renderer responses are guarded by host, Thread, composer, route and request generation. Context switches remove the old surface immediately and can load the new context while an old request is pending. Controls and errors use text-only DOM rendering. Output and process-file reads are bounded; native clipped output retains `outputTruncated` even below the local limit.

## Reopening a reviewer session

Host shutdown closes loaded Harness processes, while the Mapping Store retains the native Session reference for resume. Reopening the same Grok chat resumes that native Session and discovers its saved schedules; creating a new chat is a separate Session. A local Loop does not execute while its owning Grok process is closed.

The inspected Grok 1.0.45 source restores recurring schedules from session resources, including schedules marked `durable=false`; its native `recurring_task_survives_restart_and_rearms` regression covers that path. The flag alone does not establish that a recurring Loop disappears on a same-Session process restart. Native expiry still applies. Actual installed recovery requires confirming the same native Session, one schedule, its cadence/expiry and a subsequent native firing after reopening. Do not create a replacement Loop merely because the panel is initially empty.

Idle release preserves resume metadata but excludes sessions with known background work, including registered Loops. Cancelling a parent Turn does not unload its Harness process or delete the schedule. No immediate per-chat unload operation is exposed; deleting a schedule to make a session eligible for release changes its work and is not a memory diagnostic.
